# 极简截屏工具

一个常驻内存不到 200 KB 的 Windows 截屏工具。纯 Win32 API，无第三方库，无构建系统，编译产物是**单个 142 KB 的 exe**，不依赖任何运行库。

按 `Ctrl+Alt+Q` → 拖拽选区 → 截图自动存盘 + 复制到剪贴板 + 贴在屏幕上当参考图。

## 实测数据

在 Windows 11（2560×1600 @150%）上实测：

| 指标 | 数值 |
|---|---|
| exe 体积 | 145,920 字节（约 142 KB） |
| 空闲私有工作集 | **约 192 KB** |
| 空闲 GDI 对象 | **0** |
| 空闲 USER 对象 | 3 |
| 运行库依赖 | **无**（静态 CRT，不需要 VC++ 运行库） |
| 依赖的系统 DLL | 7 个（全部是 Windows 自带的） |
| 源码 | 1630 行 |
| 编译警告 | `/W4` 零警告 |

依赖清单：

```
USER32.dll  GDI32.dll  SHELL32.dll  ole32.dll
dwmapi.dll  COMDLG32.dll  KERNEL32.dll
```

`windowscodecs`（PNG 编码）不在导入表里 —— 它由 COM 在截图时才动态加载，用完即卸。

> **关于峰值内存**：截图瞬间会创建一个位图，4K 分辨率下约 33 MB。这是"在屏幕上显示一张图"的固有成本，无法消除。工具的做法是截完立刻释放并主动裁剪工作集，所以**稳态**回到 200 KB 量级。判断这个项目是否达标请看稳态，不要看任务管理器的"峰值工作集"列。

## 功能

**截图**

- 全局热键 `Ctrl+Alt+Q`（可改）
- 覆盖全屏的选区界面：屏幕变暗，拖拽出的区域是**真实透明**的，显示未经处理的原始像素
- `Esc` 或右键取消
- 每次截图自动存为 PNG，同时复制到剪贴板

**贴图置顶**

截图后会立刻把图像钉在屏幕上，位置就是你拖拽的位置。

- 拖动移动
- 拖拽四角等比例缩放
- 双击关闭
- 右键菜单：复制到剪贴板 / 另存为 PNG / 打开截图文件夹 / 关闭
- 蓝色边框标识，创建瞬间会有一次亮蓝色闪烁提示

**托盘菜单**

截图 / 打开截图文件夹 / 关闭全部贴图 / 退出。支持 Explorer 重启后自动恢复图标。

## 快速开始

### 环境要求

只需要 MSVC 工具链和 Windows SDK，**不需要完整的 Visual Studio**：

- **Build Tools for Visual Studio 2022**（免费，勾选「使用 C++ 的桌面开发」工作负载，约 2 GB）
- 或者完整版 Visual Studio 2022 的任一版本（Community / Professional / Enterprise）——都行

构建脚本用 `vswhere` 自动定位工具链，所以安装版本和安装盘符任意。

### 编译

```cmd
build.bat
```

产物在 `build\screenshot_tool.exe`，直接双击运行即可，无需安装。

构建脚本会自动调用 `vcvars64.bat` 并编译 `src\*.cpp`，新增源文件不需要改脚本。

> 如果你只想用不想构建，直接去上面的[下载](#下载)拿现成的 exe 就行，不需要任何工具链。

### 开机自启（可选）

把 `build\screenshot_tool.exe` 的快捷方式放进 `shell:startup` 目录即可。不需要管理员权限，删除快捷方式即卸载。

#define SHOT_HOTKEY_VK     'Q'                      // 热键主键

## 设计说明

这个项目的核心约束是内存，下面几个决定都是围绕它做的。如果你只想用不想读代码，可以跳过。

### 两条严格分离的路径

进程里只有两种代码：**常驻路径**（消息循环、热键、托盘，永远活着）和**捕获路径**（截图、编码、贴图，跑完即全部释放）。捕获路径里的任何东西都不缓存、不池化、不预热。

更重要的是，**COM 不做常驻初始化**。绝大多数程序在 `WinMain` 开头调一次 `CoInitializeEx` 就完事，但那会把整个 COM 栈（`ole32`、`combase`、`RPCRT4`、`MSCTF`……）常驻在内存里。对一个整天待在托盘里的小工具来说，这是纯粹浪费。本项目的做法是把 `CoInitializeEx`/`CoUninitialize` 配对放在捕获路径内部，只有真正要编码 PNG 的那几毫秒里 COM 才存在。

### 唯一的常驻窗口是一个永不显示的顶层窗口

它只负责接收热键、托盘回调和 `TaskbarCreated` 广播。

这里不能用 `HWND_MESSAGE`（消息窗口）—— 消息窗口收不到广播消息，Explorer 崩溃重启后托盘图标会永久消失。一个 0×0 的隐藏顶层窗口成本只有几百字节，而且能收到 `TaskbarCreated`，图标可以自动恢复。

### 选区是窗口区域上的一个"洞"

覆盖窗用了 `SetLayeredWindowAttributes` 做蒙暗，但它的 alpha 是**整窗均匀**的，没法在蒙暗层里画出一块亮色矩形。

做法是用 `SetWindowRgn` + `CombineRgn(RGN_DIFF)` 在窗口区域上**挖一个真正的洞**，洞内是 100% 未经处理的屏幕像素。绘制全部用 `GetStockObject` 系统对象，所以每次重绘创建 **0 个 GDI 句柄**，没有东西可泄漏。

### 覆盖窗不可能出现在截图里

这不是靠"记得要隐藏"，而是靠顺序保证：

覆盖窗在鼠标抬起处理函数**内部**就 `DestroyWindow` 自己，然后才 `PostMessage` 把结果投递给常驻窗口。消息排队后才被分发，所以 `BitBlt` 执行时覆盖窗在结构上已经不存在了。

外加一句 `DwmFlush()`——没有它，`BitBlt` 可能取到上一帧已呈现的画面，截图会带一层灰蒙。这个 bug 看起来像稳定复现，实际是竞态，非常耗调试时间。

### 两个格式陷阱

**PNG 编码必须用 `32bppBGR`，不能用 `32bppBGRA`。** 32 位 `BI_RGB` DIB 的第四个字节 GDI 始终保持为 0，如果按 BGRA 编码，会忠实地写出**一张完全透明的图**。（试图靠 `memset` 成 `0xFF` 来修复是无效的——`BitBlt` 会覆盖掉那些字节。）

**剪贴板反过来，必须用 24 位。** 而且方向语义与内部 DIB **相反**：内部是自顶向下（`biHeight` 为负），剪贴板要求自底向上（`biHeight` 为正）。弄错符号会得到上下颠倒的粘贴结果。

### 贴图零拷贝接管位图

`PinCreate` 直接**取得** `Bitmap32` 的所有权，而不是复制一份。这既省掉一次全分辨率 `memcpy`，也避免了复制期间两份位图同时存在导致的内存翻倍。

失败路径也照样消耗所有权（内部会自己释放），这样调用方只有一条清理路径、不需要根据成功失败分支——这正是"读一遍就能发现泄漏"和"读不出来"的区别。

### 缩放用光标投影，而不是"主导轴胜出"

贴图缩放时，把光标位置**投影到图片的比例对角线**上：

```
w = (sx·dx·a² + sy·dy·b·a) / (a² + b²)      a,b = 原始宽高；sx,sy = ±1
```

比常见的"哪个轴移动得多就用哪个轴"更麻烦，但后者有个致命缺陷：当你沿对角线拖拽时，水平候选和垂直候选会分别落在当前尺寸的**两侧**，此时胜者翻转会让尺寸一次性跳过两者之间的整个差距。斜着拖是所有人的本能动作，所以那个 bug 必然出现。投影法是连续的，跳变不是"不太可能"而是**表达式上不可表示**。

比例永远取自**原始位图**而非当前显示尺寸，否则每次缩放都要过一次整数舍入，拖十次就肉眼可见地偏离。

### 工作集主动裁剪

每次截图结束、以及所有贴图都关闭后，调用 `SetProcessWorkingSetSize(-1, -1)` 把工作集还给系统。这是任务管理器里那个数字能回到 200 KB 量级的直接原因。

注意必须在**所有 GDI 对象释放之后**再裁剪，否则只是把刚还回去的位图页立刻换回来。

## 已知限制

**多显示器与混合 DPI 未经验证。** 开发机只有一块显示器，所以以下代码路径**写是写了，但从未在真实环境跑过**：负坐标的虚拟屏原点、跨屏拖拽选区、不同缩放比的显示器混用。单屏环境下正确不代表这些路径正确。

**贴图会占用内存。** 每张贴图必须持有自己的像素才能显示，约占 `宽 × 高 × 4` 字节 —— 一张 800×600 的贴图约 1.9 MB。这是固有成本，不是实现问题。托盘菜单的「关闭全部贴图」就是为了对冲这个。另外每张贴图长期占用 2 个 GDI 对象，而进程 GDI 配额是 10000，所以在约 3300 张贴图时会撞墙（代码里设了 64 张的硬上限，超过会明确报错而不是静默失败）。

**菜单是经典样式**，不是 Windows 11 的圆角样式。因为刻意没有链接 `comctl32` —— 它会带来约 0.5–1 MB 的常驻映射，而这只是个显示两秒的菜单。

**仅支持 Windows 10/11 及 64 位。**

**只在 Windows 11（内部版本 26200）上测试过。**

## 为什么不用现成的

Windows 自带的 `Win+Shift+S` 已经是零额外常驻开销的方案。如果你只要"随手截个图"，它赢了，这个项目没有存在必要。

自己写的价值在于**自定义工作流**：截图自动落盘、自动进剪贴板、直接钉在屏幕上当参考图，以及"它只占 200 KB 而且完全在我的控制之下"。如果你也想要这个组合，欢迎拿去改。
